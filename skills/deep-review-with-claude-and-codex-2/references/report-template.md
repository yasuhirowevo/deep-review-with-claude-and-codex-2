# レポートテンプレート

run固有の`<reviewArtifactDir>/report.md`へ、以下の構造で単体利用できるMarkdownを作る。
ヘッダーはpublish時の検証対象なので、必ず`# Deep Review:`で始める。
冒頭は短い結論、重要度別の集計、Medium以上の指摘一覧とし、実行・照合の記録は末尾にまとめる。
各見出しと一覧の「一言でいうと」には、何が起きて何に困るかが一読で伝わる同じ題名を使う。
成立条件や可能性という留保は保ち、正典ID・正典題名は各指摘末尾の監査欄へ置く。
説明は段落付きリストでまとめ、`<details>`による折りたたみを前提にしない。
本文に必要な固有語は初出箇所で短く補足し、独立した「読み方」「用語」セクションは置かない。

# Deep Review: <PR #N | branch ref>

## 件数契約

- 4重要度と6取扱いの件数表を0件でも省略しない。
- 重要度表に「マージ前対応」「必須・推奨・任意」を置かない。
- `## Critical（<N>件）`から`## Low（<N>件）`まで重要度別に分け、各詳細の件数を省略しない。
- 冒頭の検出数はPhase 4の最終集合（Phase 5の除外前）を数える。各詳細の件数はPhase 5後に残る最終集合であり、検出数 = 詳細件数 + 対応済み・受容済みの除外件数とする。
- 判断済は、その除外件数のうちMedium以上を数える。Lowは「—」。レビューAIが取扱いを分類しただけでは、既存の対応判断を確認した件数へ加えない。
- 本PRの最終指摘と別Issue候補は、Phase 5後のfinal集合だけを`handling = separate-issue`かどうかで分け、Lowを含む各重要度で数える。除外済みの別Issue候補はいずれの最終件数にも加えない。両列の合計は各重要度の詳細件数と一致する。
- クロスチェック表はPhase 5後に残る最終findingだけを安定したFinding IDで1件1行にし、
  各詳細の人間向けID・表示題名・最終重要度と一致させる。取扱いと訂正理由は詳細で保持する。
- 今回の取扱い件数は`phase5/final-findings.json`の全decisionを含み、
  対応済み・受容済みで最終findingから除外された項目も数える。
- ユーザー判断が必要なfindingには`ユーザーへの確認事項`と`選択による影響`を必須とし、
  Medium以上の一覧直下へ同じ人間向けIDと文面を転記する。Lowでユーザー判断が必要な場合も確認事項の表には含める。該当がなければ確認事項の小見出し・表は省く。
- 追加確認が必要なfindingには`未確認の内容・理由と判断への影響`を必須とする。
- 除外表はPhase 5で除外された全decisionをFinding IDで1件1行にし、正典artifactの題名、
  元重要度、今回の取扱い、取扱いの根拠と一致させる。
- 再提起したfindingの`既存判断との照合`は、正典artifactの根拠種別と内容に一致させる。
- 初回reviewは`phase2/status.json`のattempt 1、round状態は各roundの正典attemptから記載する。
- `retry / resume / 失敗`はPhase 2、round 1から順に全attempt履歴を走査して導出する。初回失敗、
  attempt 2以降、中断をそれぞれ
  `<scope> <Claude|Codex> attempt <N> <initial|retry|resume> <成功|失敗|未起動>`、
  `<scope> attempt <N> 中断`の順で`; `区切りにし、該当が無い場合だけ`なし`と記載する。
  `scope`は`Phase 2`または`round <N>`とする。
- round表は正典化した`phase4/round-*`を省略せず、1から連続する全roundを記載する。
  wave固有領域に残る中断済み・完了済み非採用の投機roundは記載しない。
- round表のClaude新規から最終集合変化までは各roundの`adjudication.json`から転記し、
  全候補の判定記録から導出された値と一致させる。
- `final finding-set digest`はfinal集合digest、`handling digest`は全Phase 5 decisionのhandling digestと一致させる。
- Phase 2と全roundはretry/resume後の正典結果がClaude/Codexとも成功していなければならない。
  片方または両方が失敗したままのrunは完成reportを作らず、未完了としてユーザーへ報告する。
- `収束`と記載する場合、round表の末尾2行は両モデルとも成功、新規0件、撤回・降格・昇格0件、
  最終集合変化なしにする。
- `未収束`と記載する完成reportは、上限の20roundを全て記載する。
- 1〜19roundで収束条件を満たしていないrunは完成reportとして公開しない。
- PRコメントの判定内訳、件数集計、件数式は`phase5/final-findings.json`から転記し、
  `X = Z + R`、`Y = R`を満たして`Y`を最終finding数と一致させる。
- PRコメントの取得状態、4 sourceの件数、対象repository host・repository・PR・HEAD世代を
  run固有artifactと一致させる。
- 0件の重要度sectionは`> 該当なし`と記載し、finding見出しを置かない。

## 品質契約

重要度、7観点、finding根拠、今回の取扱い、既存判断の再提起、修正案の評価は
[review-quality-contract.md](review-quality-contract.md)を正典とする。
Critical / High / Mediumのfindingはテンプレートに示す全項目を含める。
Lowも今回の取扱い、取扱いの根拠、目的との関係、既存判断との照合、
既存成功記録との照合、場所、成立条件、影響、根拠、コードパス、確認した防御、
検出、修正案、監査欄の正典ID・正典題名・モデル別重要度・最終重要度の理由・出典を記載する。
表示用の題名を整えても、重要度と監査欄の`正典ID`・`正典題名`は
`phase5/final-findings.json`のfinal集合から変更しない。人間向けIDと正典IDは一対一とする。
`この指摘で未確認の点`には事実の未確認とその理由・判断への影響、`対処案`には変更方針と採用した場合の確認方法を分けて記載する。レビュー中に安全に実施できる確認は実施し、できなかった理由を残す。
実施済みの確認と失敗・未実施の区別は保存し、見出しの平易化を理由に根拠や条件を削らない。

必須fieldは空欄やplaceholderを残さない。公開前に`validate-review-report.mjs`で
構造、値、件数、Phase 5の取扱いとの一致を検証する。validationを通すためにfindingを
移動・削除・重要度変更せず、Phase 3〜5で確定した集合にレポートを合わせる。

## 表示と集計の補足

- Medium以上の一覧は、本PRの表と`### 別Issue候補（Medium以上）`の表に分け、最終集合の全Critical / High / Mediumを1件ずつ載せる。別Issue候補だけを後者へ置き、ID・題名・取扱い・状態を保持する。各区分が0件なら「> 該当なし」を残し、別Issue候補の小見出しを省略しない。
- 詳細4重要度、クロスチェック、監査の取扱い件数・件数式・digestは、別Issue候補も含めた従来の全件を保持する。
- 見出し・一覧・クロスチェックの人間向けIDと表示題名は揃え、正典IDとは一対一に対応させる。正典IDと正典題名は監査欄から照合する。
- 状態は観測できた修正状況だけを記載する。未確認と対象外以外の値には、各詳細で状態の根拠を示す。取扱いは既存の6分類を維持し、修正状況から推測しない。
- 両モデルの重要度は、初回から最後の正典roundまでの採否記録で同じfindingに紐付いたnew / duplicate候補を辿り、各モデルの直近の判定を転記する。再検出なしは未実行と区別する。
- ラウンド別の重要度表には初回と全正典roundを載せる。Claude / Codexはその回の正式出力の全候補、統合後は採否記録のafter.findingsを重要度別に数える。新規採用数と取り違えず、0件も記載する。投機roundは含めない。
- 表セル内のリテラル`|`は`\|`とエスケープする。表示用バッククォートは照合時に除かれるが、正典題名はMarkdownを含む元の値を保持する。
- 対応済み・受容済みの指摘はPhase 5で除外した全findingを、題名・元重要度・取扱いの根拠とともにFinding ID昇順で残す。Phase 2〜4で棄却・撤回した候補は各adjudication.jsonのrejected / withdrawnを段階順に省略せず記載する。該当なしなら各小見出しに「> 該当なし」を置く。
- branchモードのPRコメント照合は「PR未作成のため不適用」とする。PRモードでは最終取得snapshotのbot除外・重複排除後件数を使い、not-checkedなら除外0、Phase4=継続=最終を維持する。

表示名の「既存の対策で、この問題を防げるか」「変更の大きさと必要性」「修正案を採用した場合の確認方法」は、品質契約の防御確認・proportionality・追加検証に対応する。基準自体は変更しない。
